# 记忆系统核心优势 — Token 成本收益分析

> 基于 SMS v4 的全口径成本核算

---

## 一、固定开销（每会话必烧）

| 项目 | Token 数 | 说明 |
|------|----------|------|
| 记忆规则注入 | ~1,600 | CLAUDE.md / AGENTS.md 中英文混合 |
| Hot 层记忆条目 | ~500 | 6 条 × ~80 tokens/条 |
| 记忆索引 | ~200 | 简要索引 |
| **固定开销合计** | **~2,300** | 每会话必付 |

## 二、可变开销（按操作计费）

| 操作 | Token/次 | 频次 |
|------|----------|------|
| 记忆检索 | ~250 | 会话启动 1 次 |
| 语义搜索 | ~400-600 | 每次搜索 1-3 次/会话 |
| 写入/合并 | ~600-1,000 | 每次记录 2-8 次/会话 |
| 压缩维护 | ~1,500/天 | 定期巡检 + 维护 |
| 决策评估 | ~100/次 | 对话中隐形消耗 |

## 三、节省项（无记忆体时的浪费）

这是核心——记忆系统代替了什么：

| 场景 | 小型会话 | 大型项目会话 |
|------|----------|-------------|
| 用户重新说明技术栈/架构 | 300-800 | 2,000-4,000 |
| 偏好纠正（格式、命名、工具） | 200-500 | 500-1,200 |
| 错误假设导致的返工对话 | 500-1,500 | 3,000-8,000 |
| "上次怎么解决的？" 回溯 | 200-800 | 2,000-5,000 |
| 已知 bug 重复踩坑 | — | 3,000-10,000 |
| **单会话节省合计** | **1,200-3,600** | **10,500-28,200** |

### 回本点（Break-even）

这是图最重要的地方。

```
第一次：
  无记忆 = 2000
  有记忆 = 2300
  亏 300 ❌

第二次：
  无记忆 = 4000
  有记忆 = 2500
  赚 1500 ✅
```

**第二次会话就已经回本。**

这就是图里的拐点。之后的每次会话都是纯赚。

| 场景 | 回本时点 | ROI |
|------|---------|-----|
| 小型场景（日常聊天） | 第 2-3 次会话 | 1.5-3x |
| 中型场景（连续开发） | 第 1-2 次会话 | 3-8x |
| 大型项目（30 天+） | 首次即回本 | 5-20x |

## 六、压缩机制 Token 消耗详解

### 单次压缩的真实 Token 账单（10 条记忆）

| 操作 | Token 消耗 |
|------|-----------|
| Monitor 触发 prompt | 300-500 |
| get_stats() 调用往返 | 500-800 |
| get_context() 拉取 Hot+Warm | 700-1,200 |
| 模型分析 & 合并决策 | 500-1,000 |
| write_or_merge() 执行合并 | 600-1,200 |
| 确认 & 日志 | 200-400 |
| **单次触发合计** | **~3,500** |

### 每日层级维护（0 点定时）

| 操作 | Token 消耗 |
|------|-----------|
| Cron 触发 prompt | 200-400 |
| 全量 get_context + get_stats | 1,200-1,800 |
| 评分重算 & 层级决策 | 500-800 |
| 层级移动操作 | 300-600 |
| **每日维护合计** | **~2,800** |

每日压缩总消耗 ≈ 3,500 × N次触发 + 2,800（按每天 2-4 次空闲触发估算）→ **~10,000-15,000 tok/day**

---

### 会不会指数级增长？答案：不会

#### 原因：三个硬上限

```
条目数
│
10000 ─┤ ⟋ Cold（无限制，不进上下文）
 │ ⟋
1000 ─┤ ⟋╱
 │ ⟋╱
120 ─┤───────────⟋╱────────── Warm 上限 100 + Hot 上限 20
 │ ⟋╱ ← 上下文只加载这 120 条
20 ─┤────⟋╱────────────────── Hot 上限 20
 │ ⟋╱
0 ─┴╱────────────────────────▶ 时间
 首次 1周 1月 3月 1年
```

> 压缩只扫描 Hot+Warm（≤ 120 条），不碰 Cold。120 条是常数上界——跟总条目 10 条还是 10,000 条无关。

#### 增长曲线对比

```
Token 消耗
│
│ ╭── 指数增长（理论最坏）
│ ╭─╯
│ ╭──╯
│ ╭──╯
│ ╭╮──╯
│ ╭──╯╰────────────────── 线性增长 O(n)
│ ╭──╯
│ ╭──╯
│╭─╯ ╭────────────────────────── 实际增长 O(1) 有界
││╭──╯
╰╯────────────────────────────────▶ 总记忆条目数
 0 20 50 100 200 500 1k 5k 10k
 ↑
 达到上限后不再增长（Hot 20 + Warm 100 = 120）
```

#### 各操作复杂度对比

| 操作 | 10 条 | 1,000 条 | 10,000 条 |
|------|-------|---------|----------|
| get_context() 拉取 | ~1,000 tok | ~3,500 tok | ~3,500 tok ← 封顶! |
| search_fts() 搜索 | ~400 tok | ~600 tok | ~800 tok |
| write_or_merge() 写入 | ~600 tok | ~600 tok | ~600 tok |
| 模型分析 & 合并决策 | ~1,000 tok | ~5,000 tok | ~5,000 tok ← 封顶! |
| 层级维护 | ~2,800 tok | ~8,000 tok | ~8,000 tok ← 线性可批处理 |
| **单次压缩总计** | **~3,500 tok** | **~8,000 tok** | **~8,000 tok ← 几乎不变** |

**1,000 条 vs 10,000 条，压缩成本几乎不变。** 唯一线性增长的是层级维护（需遍历全量评分），但这是 O(n) 不是 O(n²)，且可以分批降频。

- 30 天项目：日均压缩 ~6,000 tok，累计 ~180,000 tok
- 365 天项目：日均压缩 ~7,500 tok，累计 ~2,700,000 tok

> 注意：压缩消耗的 token 全部来自空闲触发的 Monitor（非活跃对话时间），不占用用户交互的上下文窗口。层级维护在凌晨 0 点执行，同样不影响正常使用。

---

### 一句话总结

> **压缩成本是 O(1) 有界函数，不是指数增长。**
>
> 1,000 条记忆和 10,000 条记忆的压缩消耗几乎一样，
> 因为 Hot+Warm 硬上限 = 120 条，Cold 不参与压缩。
>
> 真正的增长来自「层级维护需要遍历全量条目」，但那是 O(n) 线性，
> 可以批处理、可以降频，永远到不了指数级。
>
> 唯一需要担心的是 0 点层级维护在全量条目很大时（比如 10 万+ 条 Cold）
> 的单次遍历成本。不过目前只有 10 条，Cold 层完全空着。
> 真要到了那个量级，把维护频率从「每天」降到「每周」就解决了。

## 七、隐性收益（无法量化但更值钱）

| 收益 | 为什么值钱 |
|------|-----------|
| **避免重复踩坑** | 一个已知 bug 重演 = 浪费 2,000-10,000 tokens 排查 |
| **决策一致性** | 不会这周选 A 下周选 B，避免架构漂移 |
| **知识压缩率** | 一条 80-token 记忆可替代 500-2,000 token 的对话回溯 |
| **上下文窗口释放** | 省下的 token 用来装更多实际代码和逻辑 |

## 八、核心结论

**核心公式：记忆系统的价值 ∝ 项目规模 × 会话次数 × 记忆密度**

- **小型场景（日常聊天）：** ROI ≈ 1.5-3x，回本周期 2-3 次会话
- **中型场景（连续开发）：** ROI ≈ 3-8x，回本周期 1-2 次会话
- **大型项目（30 天+）：** ROI ≈ 5-20x，首次即回本

### 当前状态

- 10 条记忆（主要是偏好）→ ROI ~1.5-2x
- 若积累到 60+ 条项目级记忆 → ROI 可达 5-10x

### 一句话总结

> **没有记忆系统时，每次开新会话等于"失忆症患者重新认识项目"，那才是真正的 token 黑洞。**
> 首次会话小亏，第 2 次回本，之后纯赚。
> 记忆越多，收益越大。
